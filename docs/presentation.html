Career Fair Eligibility Shortlist

Samyak Sanklecha · Problem SI26_P06

A small offline rules engine: it checks one student profile against five fixed career-fair roles, and for every ineligible role shows exactly which rules failed.

Approach

How I built it — a 5-step plan

Test-driven from the start: the acceptance criteria became tests before any logic was written.

  1. Understand the spec — extract functional & non-functional requirements.
  2. Choose the tech stack — the simplest thing that fits the scope.
  3. Design — high-level & low-level architecture + the key data-structure decisions.
  4. Write the test suite first — encode every acceptance criterion and edge case.
  5. Implement to green — build function by function, then verify end-to-end and add CI.
Architecture

Architecture & stack

Vanilla HTML + CSS + JavaScript — no framework, no build step, no dependencies.

  • logic.js — pure functions, DOM-free
  • index.html — the user interface
  • tests.js — 65-test suite (node tests.js)

Why: it fits the scope (the brief warns against over-engineering), I can explain every line, there’s instant refresh for live edits, and keeping the logic DOM-free is what lets the UI and the tests call the same functions.

Single entry point: runEvaluation().

Design decisions · 1 / 2

Data & rules

Roles are data-driven, not hardcoded
The five roles live in a config array; one generic evaluateRole(profile, role) applies the same five checks to any role.
Alternative: hardcode each role’s logic separately. Why not: adding a role would mean writing and testing new code, and the data gets tangled with the logic. As data, adding a role is a one-line change — which also makes the most likely live modification (“add a role”) trivial. This is configuration over code.
Every rule is evaluated — no short-circuit
An ineligible role must list every failed rule, so evaluation collects all failures instead of stopping at the first.
Deliberate asymmetry: profile validation does the opposite — it stops at the first invalid field and shows one message, because a malformed profile can’t be evaluated at all. The spec models these two differently on purpose, and matching that shows careful reading.
Design decisions · 2 / 2

Validation & rendering

Strict numeric validation
Used Number(), not parseInt / parseFloat, plus a regex guard so only plain decimal input passes.
Why: parseInt("2027.5") returns 2027 — it would silently accept a non-integer year. Number() validates the whole string. I also reject hex / scientific forms like 0x7EB or 2e3 that Number() would otherwise treat as valid. That’s stricter than the literal spec, so I documented it as an assumption.
Rendered with textContent, not innerHTML
All dynamic content is written via textContent / DOM methods.
Why: branch and skills come from user input; building HTML strings with innerHTML would open an injection risk. textContent avoids it entirely — a cheap, correct habit.

Judgment over reflex: I applied patterns where they pay off (data-driven roles), and declined a declarative rule-list where it would have been over-engineering for five fixed rules.

AI workflow

How I worked with AI

  • Test-driven with AI — I turned the acceptance criteria into an executable suite first, then implemented until red turned green. The tests gave the AI an exact target on every prompt.
  • Deliberate context management — fed the spec once and referred to it by name, kept everything in a few small files, and scoped each prompt to one artifact to avoid wasteful regeneration.
  • Iterated, didn’t accept blindly — e.g. I noticed 2e3 was slipping through year validation and hardened it (test first, then the guard), and questioned Number() vs parseInt.
  • Verified every output — I read the generated code and ran it; the solution is mine, not pasted.
